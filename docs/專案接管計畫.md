# 專案接管計畫

> 建立日期：2026-08-07
> 範圍：`C:\question`（依 `AGENTS.md`，不主動處理 `single/`）

## 1. 接管目標

把目前以 Live2D 為共同資產、由多人搶答、桌面寵物、題庫工具與硬體整合組成的專案，整理成可持續開發、可驗證、可安全操作的系統；接管期間優先維持既有行為，避免為了重構而破壞可用流程。

接管後的工作原則：

- 先釐清現況與驗證行為，再修改程式。
- 以 `CONTEXT.md`、`docs/adr/` 和既有規格為設計依據；若新需求與 ADR 衝突，先明確提出。
- 每次變更只處理一個清楚目的，附上相應測試或手動驗證紀錄。
- 保留使用者既有的未提交變更，不擅自重設、覆寫或清除。

## 3. 第一階段：建立可相信的基線

1. 記錄目前 Git 工作區的未提交內容，區分既有工作與後續新增變更。
2. 確認每個可執行子系統的啟動方式、埠號、外部依賴與所需憑證。
3. 執行現有自動測試；目前 `desktop-pet` 的 Vitest 基線為 8 個測試檔、80 個測試。
4. 為多人搶答整理最小手動驗證流程：主持人建局、玩家加入、作答、結算、重連與主持人離線。
5. 把無法在本機自動驗證的依賴（Mosquitto、Node-RED、ESP32、Ollama、OpenAI API）列為明確前置條件，而不是默認假設。

第一階段完成條件：任何人都能依文件判斷「哪個子系統可跑、缺什麼、如何驗證」，且不必從程式碼猜測。

## 4. 第二階段：完成桌面寵物的在途功能

目前工作區的未提交內容主要集中於 `desktop-pet/`，因此先以最小範圍完成該區域。

### 4.1 聊天 provider

- 保持 OpenAI 為預設路徑，Ollama 是使用者主動選擇的替代 provider。
- 驗證 Ollama 位址正規化、模型列表、連線失敗訊息與 OpenAI 設定互不干擾。
- API key 不回傳給 renderer，不將它印入終端日誌或錯誤訊息。

### 4.2 Claude CLI 模式

- 將模式進入／退出、工具呼叫、使用者確認、取消與錯誤恢復視為完整狀態機驗證。
- 維持「操作前逐步確認」這條安全邊界，不以便利性跳過確認。
- 清楚標記此模式會在本機執行任務；若要擴大權限或工作目錄範圍，必須先取得使用者明確同意。
- 防範從網頁摘要或聊天內容帶入的提示詞注入，不把模型輸出直接等同於已授權操作。

### 4.3 UI 與 Live2D

- 以文字泡泡定位、換行、播放完成延遲收合、使用者中途打斷為驗收情境。
- 對共用檔 `lib/live2d.js` 的修改，同時檢查桌面寵物與多人搶答，避免修正其中一端卻影響另一端。

第二階段完成條件：在途功能有規格、單元測試與可重複的人工驗收結果，並以小型、可審閱的提交保存。

## 5. 第三階段：穩定多人搶答與硬體整合

### 多人搶答

- 將 `host.html` 與 `player.html` 的 MQTT topic、狀態、保留訊息和離線行為整理成一份協定表。
- 優先測試高風險情境：重複加入、延遲作答、主持人斷線、玩家重連、不同遊戲模式與題庫格式錯誤。
- 在不改變功能的前提下，逐步把過大的內嵌腳本拆成可獨立測試的模組；每一步都維持頁面可直接開啟。

### 硬體與區網

- 把 Mosquitto、Caddy、Node-RED、ESP32 的位址、埠號與 topic 設定集中列出，避免散落在程式與流程 JSON 中。
- 將目前適用於受信任內網的設定明確標示；若提供網際網路存取，需先加入 MQTT 驗證、ACL、TLS 與網路隔離。
- 保留「硬體離線不影響遊戲核心」的既有設計原則。

## 6. 品質與交付規則

- JavaScript 功能：優先為純邏輯撰寫 Vitest 測試；UI、Electron、MQTT 與硬體部分附人工驗證步驟。
- 題庫：在匯入前驗證題目、選項、正確答案與說明的結構。
- 文件：每個新增的外部服務或安全決策，同步補充規格或 ADR。
- Git：不混入無關格式化或產物；不覆蓋既有未提交變更；提交訊息描述使用者可見的結果。
- 安全：不在程式碼、題庫、日誌、文件範例或提交中放入 API key、token、私有網址或其他機密。

## 7. 建議的近期工作順序

1. 固定目前 `desktop-pet` 未提交功能的驗收範圍並完成測試。
2. 以一次實際區網流程驗證多人搶答的核心回合與 MQTT 重連。
3. 建立題庫 schema／驗證共用層，讓題庫編輯器與遊戲使用相同規則。
4. 整理硬體整合設定與故障排除清單。
5. 視需求再進行多人搶答前端模組化與啟動流程整合。

## 8. 需要使用者決策時才會暫停的事項

- 是否要把多人搶答與桌面寵物拆成獨立發布專案。
- 是否允許 Claude CLI 模式擴大可操作範圍，或引入額外沙盒。
- 是否要把 MQTT／Caddy 從受信任區網模式升級為對外服務。
- 是否要改用作業系統安全儲存機制保存 API key。
- 涉及實體硬體接線、Wi-Fi、broker 帳密或雲端帳號的任何變更。

## 9. 首次接管報告格式

後續每次接管工作完成時，會回報：

1. 完成的使用者可見結果。
2. 變更檔案與原因。
3. 自動／手動驗證結果。
4. 已知風險、未驗證項目與下一個最小工作單位。

# desktop-pet-web 手勢 PK 對戰模式：一個擂台端＋兩支遙控器、單一場次、防禦是持續狀態

desktop-pet-web 要新增「兩位玩家用手勢隔空對戰」的功能，兩個角色（Aatrox、Mordekaiser）在全螢幕畫面裡對打，透過區網連線。這是目前這個子專案規模最大的一次擴充，牽涉的架構決定比之前的手勢功能都多，這份 ADR 記錄幾個真的有取捨、影響後續好幾週工作量的決定。

## 決定

1. **一個擂台端（顯示＋判定）＋兩支遙控器（純輸入）**，不是兩端各自完整渲染、即時同步狀態。**2026-08-18 修訂**：擂台端本身也是其中一位玩家（玩家一），不是純中立的第三方顯示器；只有玩家二是真正的「遙控器」（見文末修訂記錄）。
2. **整個區網同時只有一場對戰**，不做房間碼、不支援多場對戰同時進行。
3. **防禦手勢是持續狀態**（舉着才算防禦中），攻擊/跳躍是邊緣觸發的單次事件——兩種手勢用不同的判定邏輯，不是三個手勢都套用同一套。
4. **複用 `multi/` 現有的 MQTT broker 跟心跳/離線判定慣例**（`ws://IP:9001`、`HEARTBEAT_MS=3000`、`OFFLINE_MS=10000`），新開 `pk/*` topic 命名空間，不新架一套通訊機制。

## 為什麼是「一個擂台端＋兩支遙控器」，不是雙端各自完整同步

需求討論時列過兩種架構：(a) 一台裝置顯示完整對戰畫面、兩支手機純粹送輸入事件；(b) 兩位玩家各自在自己裝置上看到完整對戰畫面，雙方的角色位置/血量/動畫狀態要即時同步、互相校正誤差。最後選 (a)，理由：

1. **複雜度差一個量級**：(b) 是「即時多人連線遊戲」的標準難題——誰是權威狀態、延遲補償、狀態校正衝突——這些不是「新增一個功能」能解決的，是全新的一套架構工作，遠超這次的規模。(a) 的操控端完全不需要渲染 3D、不需要處理狀態同步，只是「鏡頭辨識手勢→發一個事件」，複雜度跟現有的 `AatroxGestureTrigger.tsx` 是同一個量級。
2. **手機效能考量**：(b) 要求兩支手機都能流暢跑 WebGL 3D 渲染＋鏡頭手勢辨識＋網路同步，對手機是不小的負擔；(a) 手機只需要跑鏡頭手勢辨識，3D 渲染全部交給擂台端那台通常效能較好的裝置。
3. **跟現有基礎設施的心智模型一致**：`multi/` 的 host/player 架構就是同一種「一個顯示端＋多個純輸入的遙控端」模式，這次不是發明新東西，是把同一套模式套用到新的功能上，使用者對「主持人畫面 vs 玩家手機」這個分工已經很熟悉。

## 為什麼不做房間碼

單一場次假設代表整個區網同時只能有一場 PK 對戰，這跟 `multi/` 現有的假設一致（`multi/` 也是「同一時間一場搶答遊戲」，沒有多房間）。房間碼機制是給「同時很多人在用、需要區分誰跟誰一組」的場景設計的，這次的實際使用情境是「家用區網，通常就是主機前面兩個人輪流玩」，房間碼的額外 UI（產生代碼、輸入代碼、驗證代碼）純粹是這次用不到的複雜度。之後如果真的有「同時好幾組人在同一個區網分別對戰」的需求，才需要重新設計，不是現在的範圍。

## 為什麼防禦是持續狀態，不是邊緣觸發

攻擊、跳躍都是「做一個動作」，語意上天生適合邊緣觸發（比一次算一次），現有 `gestureTriggerState.ts` 這套模式直接適用。防禦不一樣——直覺上「舉着防禦手勢才算正在防禦，放下就沒有」，這才有「看到對方出拳、立刻舉手擋下」的即時互動感，是這個模式最核心的樂趣所在。如果把防禦也做成邊緣觸發（比一次觸發一小段無敵時間），實作上更單純（三個手勢共用同一套狀態機），但會犧牲掉這個核心互動感，變成「防禦技能」而不是「格擋」，體驗上差很多。

代價是需要多寫一個雙向邊緣偵測的狀態機（`pkDefenseState.ts`），跟需要在協定層面（`pk/input` 的 `defense` 訊息、心跳訊息裡的保底同步）多處理「這個持續狀態萬一漏掉一則訊息會不會卡住」的問題——這些都在 `docs/specs/0013` 的 Implementation Decisions 裡有具體解法，不是沒考慮過的風險。

## 影響

- 複用 `multi/` 的 broker/心跳慣例，代表這次沒有新的基礎設施要架設，`pk/*` 命名空間確保跟 `quiz/multi/*` 不衝突，兩套系統可以同時獨立運作。
- 操控端完全不做 3D 渲染，代表這次的「擂台端」是唯一需要處理 three.js 雙角色場景/命中判定/動畫混合的地方，複雜度集中在 `PkArenaView.tsx`＋`pkMatchState.ts`，操控端（`PkControllerView.tsx`）相對單純，量體接近既有的 `AatroxGestureTrigger.tsx`。
- 如果之後真的想要「雙端各自完整同步渲染」（例如想做成真正的連線對戰遊戲，不侷限同一區網主機前面），那是全新的一輪設計（狀態同步、延遲補償），不是這次架構的自然延伸，屆時應該另開 ADR，不要預設可以直接沿用這次的實作。
- 如果之後想要支援多場對戰同時進行，需要重新設計 topic 命名（例如每場對戰一個隨機 ID 當 topic 前綴）跟房間碼 UI，這也是全新的一輪設計，不是改一兩個常數就好。

## 修訂記錄

**2026-08-18：擂台端本人變成玩家一，只剩一支遙控器（玩家二）**

原始決定是「擂台端純顯示＋判定，兩位玩家都各自用手機當遙控器」，需要兩支手機才能開一場。使用者實際用過後提出更貼近真實使用情境的流程：**擂台端操作者（通常是主持這台電腦的人）本人就是玩家一**，開場不用等，只要有一個人掃 QR code 加入就自動變成玩家二、遊戲直接開始。改成這樣的理由：

1. **降低開局門檻**：原設計每場都要湊到兩支手機，這次改成「一台電腦（自帶鏡頭）＋一支朋友的手機」就能玩，更符合「臨時想玩一場」的實際情境。
2. **不影響已經定案的核心架構**：`pkMatchState.ts` 的比賽狀態機骨幹沒有變動——兩個 slot 都填滿才開始倒數，玩家一現在用一個固定的本機 `playerId`（`LOCAL_PLAYER_ID`）在鏡頭授權成功那一刻直接呼叫 `applyJoin()`，跟遠端玩家透過 `pk/join` 訊息呼叫是同一個函式、同一套規則。（**2026-08-18 補充修正**：`applyJoin()` 原本是「哪個 slot 空就填哪個」，實測發現如果玩家二的 `pk/join` 剛好搶在玩家一本機 join 之前抵達，玩家二會被誤塞進 player1，玩家一自己反而變成 player2——已修正成 `applyJoin()` 要求呼叫端明確指定 `targetSlot`，本機呼叫永遠指定 `'player1'`、MQTT 收到的訊息永遠指定 `'player2'`，跟到達順序無關，見下面新增的修訂記錄。）
3. **「一個擂台端＋一支遙控器」沒有違背決定 1 的核心精神**：真正要守住的是「不要兩端各自完整渲染、即時同步狀態」（見上面「為什麼是一個擂台端＋兩支遙控器」），這一點完全沒變——擂台端還是唯一做 3D 渲染／命中判定的地方，玩家一的鏡頭只是多了一組「這台裝置自己辨識自己的手勢」的邏輯，跟原本「遠端玩家的手勢由操控端辨識、透過 MQTT 通知擂台端」在架構上是對稱的兩條輸入來源，不是新的一種角色。

**影響**：`PkArenaView.tsx` 新增一組跟 `PkControllerView.tsx` 對稱的鏡頭/手勢辨識邏輯（給玩家一本人用），透過 ref 直接呼叫比賽狀態機（不繞 MQTT 自己發給自己），細節見 `docs/specs/0013` 的更新。「確保有攝影機授權功能」這個要求具體落地在：鏡頭真的授權成功才會把玩家一加入比賽，避免比賽開始了玩家一卻因為沒授權而完全無法出手的破圖狀態；授權失敗有明確錯誤訊息＋可重試的按鈕，不會卡死整個 PK 模式。

**2026-08-18：`applyJoin()` 的 slot 分配從「哪個空就填哪個」改成「呼叫端指定 targetSlot」**

上一條修訂讓玩家一（擂台端本人）用本機呼叫、玩家二用 MQTT `pk/join`，但兩者最終都還是呼叫同一個 `applyJoin(state, playerId, now)`，而這個函式原本的邏輯是「player1 是 null 就填 player1、否則填 player2」——完全不知道呼叫端「應該」是誰。使用者實測回報：換一台裝置當玩家二連線，畫面卻顯示自己是玩家一。根因是玩家二的 `pk/join` 訊息剛好比玩家一本機的 `joinAsPlayer1Ref` 呼叫早抵達（玩家一要等使用者真的點了鏡頭權限彈窗，比遠端 MQTT 訊息的網路延遲慢是完全可能發生的），這時候 `player1` 這個 slot 還是空的，玩家二就直接填進去了。

**決定**：`applyJoin()` 新增第四個參數 `targetSlot: PlayerSlot`，由呼叫端明確指定要塞哪個 slot，不再靠「哪個空就填哪個」猜。`PkArenaView.tsx` 的兩個呼叫點分別寫死：本機呼叫永遠傳 `'player1'`、MQTT `pk/join` 收到的訊息永遠傳 `'player2'`。跟到達順序完全無關，`pkMatchState.test.ts` 新增測試鎖住「玩家二先 join 也不會占走玩家一的位置」。

**2026-08-18：新增移動控制＋攻擊改成需要距離夠近（部分推翻先前「不做真正的空間碰撞/距離判定」的決定）**

先前「為什麼不做房間碼」附近的討論脈絡裡，命中判定的原始決定是「純手勢節奏對抗，跟角色 3D 位置完全無關」（見 `docs/specs/0013` 舊版「手勢輸入與命中判定」）。使用者實際玩過後要求改成更像真正格鬥遊戲的手感：**手在鏡頭畫面左右位置連續控制角色前進/後退，攻擊要真的靠近對方身體才會命中**。這是對原始決定的部分推翻，記錄如下：

1. **為什麼還是不做完整的空間碰撞系統**：加入移動＋距離判定，不代表整個變成物理碰撞/格鬥遊戲等級的位置系統——移動只有一個自由度（沿着面對面那條軸前進/後退，不能左右閃避、不能繞背），命中判定只看「兩個角色中心點的距離是否小於某個依身高換算的閾值」，不是真的碰撞盒相交測試。複雜度介於「純狀態對抗」（原本）跟「完整格鬥遊戲物理」之間，量體可控。
2. **移動用連續手部位置，不是離散手勢**：攻擊/跳躍/防禦都是「手勢分類」（Closed_Fist/Victory/Open_Palm），移動改用 MediaPipe 回報的 landmark 座標（連續數值），跟手的形狀無關——這樣移動可以跟任何手勢同時發生（邊移動邊防禦、邊移動邊準備攻擊），不會因為「移動也要占用一種手勢分類」而互相打架。新增 `pkMovement.ts` 這個純函式模組（`handToMoveValue()`），跟 `pkDefenseState.ts`／`pkEdgeTriggerState.ts` 一樣刻意保持不碰 MediaPipe/three.js，方便單元測試。
3. **移動不進 `pkMatchState.ts` 的比賽狀態機**：跟跳躍是同一種處理——純視覺位置效果，只存在於 `PkArenaView.tsx` 的 `CharacterRig.moveInput`／`root.position`，不透過 wire protocol 同步玩家位置給操控端（操控端本來就不做 3D 渲染，不需要知道位置）。這保留了原始決定 1（「一個擂台端＋兩支遙控器」）的核心精神：位置狀態只存在擂台端這一份，不需要處理「兩端位置要不要同步/校正誤差」的問題。
4. **攻擊距離判定在擂台端本機做，不進狀態機**：`applyInput()` 的 reducer 完全不知道「距離」這個概念，範圍檢查（`isWithinAttackRange()`）在 `PkArenaView.tsx` 收到攻擊事件當下、呼叫 `applyInput()` 之前先做——搆不到就直接不呼叫 reducer（不扣血），但動作照樣揮出去（揮空的視覺回饋）。維持 `pkMatchState.ts` 單純只管「規則」（血量/回合/連線），不沾染任何空間座標概念，是刻意的分工。

**影響**：新增 `pk/input` 的 `'move'` 訊息類型（連續數值，`PkControllerView.tsx` 節流到 10Hz 發布，`PkArenaView.tsx` 本機每幀直接呼叫不需節流）；新增 `ATTACK_RANGE_HEIGHT_RATIO`／`MOVE_SPEED_HEIGHT_RATIO`／`MIN_GAP_HEIGHT_RATIO` 這幾個依角色身高換算的可調常數，不是寫死的絕對數字。角色移動範圍限制在「不能退得比出生點遠」＋「不能貼到/穿過對方」，兩個角色一起算的邊界檢查（`clampMutualGap()`）。這幾個具體數字都還沒有實機測過手感，跟先前的攻擊/防禦動畫選擇一樣，之後很可能要調。

**2026-08-18：新增操控端同步看擂台端畫面（WebRTC 視訊串流）——不違背決定 1 的核心理由**

使用者要求玩家二的手機也能看到擂台端目前的畫面，不是只有文字狀態（血量條/倒數數字）。這聽起來像是要推翻「操控端完全不做 3D 渲染」，但實際做法不是——區分清楚：

1. **操控端還是沒有自己算 3D**：畫面是擂台端用 `renderer.domElement.captureStream()` 直接擷取「自己畫出來的東西」轉成視訊串流傳過去，操控端收到的是一段影片（解碼＋播放），不是拿到座標資料自己重新渲染一份。決定 1 原本要避免的是「兩端各自算 3D、狀態要同步校正」這個複雜度，視訊串流完全不落入這個問題——串流只是「把已經算好的畫面搬過去」，沒有第二份權威狀態需要維護。
2. **手機效能負擔的疑慮改用「解碼視訊」取代「即時渲染」**：解碼播放一段 H.264/VP8 視訊串流，比起手機自己跑 WebGL 3D 渲染＋物理/動畫計算，對手機的負擔小很多且是瀏覽器原生最佳化過的路徑（`<video>` 標籤），不是本次新增的自訂運算。
3. **訊令（signaling）複用 `multi/VoiceBroadcastModule.js` 已經驗證過的 WebRTC+MQTT 模式**：offer/answer/ice 走 MQTT signaling（`pk/webrtc/signal/{targetId}`，跟 voice 的 `SIG_PREFIX + targetId` 同一種「發到收件人的信箱」定址法），公開 STUN server（`stun:stun.l.google.com:19302`，跟 `MP_CFG.VOICE_ICE_SERVERS` 同一顆）。PK 模式比 voice 單純：永遠只有一個廣播者（擂台端）＋一個觀眾（玩家二），不需要 voice 那套多對多的 `_outPeers`/`_inPeers` 字典管理。
4. **`LOCAL_PLAYER_ID` 搬到 `pkProtocol.ts` 變成共用常數**：操控端要知道「擂台端的訊令信箱在哪」才能把 pull/answer/ice 送過去，這個固定 ID 原本只有 `PkArenaView.tsx` 自己知道，現在兩邊都需要，順勢搬成共用的協定層常數。

**影響**：新增 `pk/webrtc/signal/{targetId}` topic（不是 retained，操控端用跟 `pk/join` 同一招——心跳 interval 順便重發 `pull` 直到連上，見 `docs/specs/0013` 實作備註，同一種訂閱時機競態，同一種解法）。玩家一（擂台端）自己完全不需要看這段視訊（他就在畫面前），只有玩家二會用到。這個功能失敗（WebRTC 建立不起來，例如 NAT/防火牆問題）不影響手勢輸入本身——`hostVideoStatus` 顯示「暫時無法顯示」但不擋路，操控端其餘功能照常運作，是刻意的失效隔離設計（跟手勢拖曳/手勢動作觸發一貫的態度一致）。

# 桌寵 CLI 模式新增「免確認模式」opt-in 開關，修正 ADR-0008 的「不用 bypassPermissions」決定

ADR-0008 在設計 CLI 模式時明確寫下：「**不用 `bypassPermissions` 模式**——那等於把 wake-word 誤判的風險直接放大成『誤判就等於執行』」。這份 ADR 記錄後來為什麼還是加了一個能達到類似效果的開關，以及加的時候做了哪些取捨，讓 ADR-0008 沒有失真。

## 為什麼要改

使用者每次 CLI 模式的風險操作都要逐句回覆「同意」，覺得太打斷任務節奏，想要一個可以跳過逐步確認的模式。這是使用者對自己單機自用工具的產品決定（見 ADR-0008「CLAUDE.md 記錄的專案定位是純自用」的前提沒變），不是被便利性說服而擅自放寬安全邊界。

## 沒有走 `bypassPermissions`，走的是「opt-in 開關 + 保留實況描述」

ADR-0008 反對的具體風險是「wake-word／訊息誤判 → 誤判當下就直接執行、使用者毫無察覺」。新增的「免確認模式」用三個設計把這個風險縮小到使用者能接受、且事後可稽核的範圍：

1. **預設關閉，且是全域設定畫面裡的獨立開關**——不會因為進入 CLI 模式就自動套用，使用者要多一個明確步驟才會啟用，跟「誤判觸發短語」是兩件獨立的事，不會被一次誤判疊加放大。
2. **開啟前二次確認**：跟清除 API key／清空對話記憶同一套 `dialog.showMessageBox` 原生警告對話框，把「這會拿掉哪道防線」寫在警告文字裡，不是一個不起眼的勾選框。
3. **仍然保留即時實況描述**：`canUseTool` 在免確認模式下不再暫停等待使用者回覆，但每次自動放行風險操作前都會先透過 `onNarration` 把「做了什麼」送到桌寵的文字泡泡＋語音——不是完全靜默執行。使用者事後（甚至當下，如果有在看畫面）都能發現它做了什麼，跟真正的 `bypassPermissions`（SDK 層級整個跳過 `canUseTool`、沒有任何呼叫端可以攔截或記錄）不同。

換句話說：拿掉的是「暫停等回覆」，沒拿掉「讓使用者知道發生了什麼」。ADR-0008 那句「這個功能的安全性最終還是依賴使用者自己在確認時真的有看清楚在同意什麼」在免確認模式下變成「依賴使用者確實有在看螢幕、且清楚自己交代的任務範圍」——風險的性質改變了，不是被消除了，這是使用者知情之下接受的取捨。

## 沒有解決、刻意先不擋的風險

- 免確認模式開啟期間，如果觸發短語本身被誤判（例如語音誤聽成「進入 CLI 模式」），緊接著的訊息會被當成任務 prompt 直接送給 Claude 執行，且風險操作不會暫停——這正是 ADR-0008 原本要防的情境，免確認模式開啟時這道防線確實是不在的。緩解手段只有「預設關閉＋開啟需要主動二次確認＋用完提醒關閉」，沒有技術手段能在開啟期間完全消除這個風險。
- `onNarration` 的訊息是「做了之後才通知」（allow 判斷完、真正執行前才送出），不是「做之前先問你要不要」，使用者沒有機會在單一操作發生前喊停，只能透過「退出 CLI 模式」中止後續任務。

## 範圍界定

- 全域開關（兩個角色共用），不是 per-character——跟「即時對話 AI 提供者」那類設定同一個範圍慣例。
- 只影響**建立 session 當下**讀到的值；同一個 CLI 模式 session 進行中途在設定畫面切換，不會讓正在跑的任務行為突變，要退出再重新進入 CLI 模式才會套用新值。
- `SAFE_TOOLS`（`Read`/`Glob`/`Grep`）的行為完全不受影響——免確認模式只改變「原本需要確認的操作」變成「自動放行＋事後告知」，唯讀操作原本就不需要確認也不需要額外告知。

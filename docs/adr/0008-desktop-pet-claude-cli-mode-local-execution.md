# 桌寵開放「CLI 模式」：對話觸發本機 Claude Code 執行任務，逐步確認風險操作

桌寵的即時對話（`docs/specs/0002`）跟本機 Ollama（`docs/specs/0005`）都只會「生成文字」，不會碰觸使用者的檔案系統或執行任何指令。這份 ADR 記錄一個性質完全不同的決定：讓桌寵對話能觸發**本機任意程式碼執行**——透過 Claude Agent SDK（`@anthropic-ai/claude-agent-sdk`）呼叫 Claude Code，在使用者的專案目錄（預設 `C:\question`）讀寫檔案、執行 shell 指令。

## 為什麼願意做這麼高風險的功能

CLAUDE.md 記錄的專案定位是純自用（見 ADR-0001 對「不用顧慮多使用者」的引用）。使用者本來就在同一台機器上用 Claude Code CLI 工作，這個功能只是換一個更方便的觸發入口（跟桌寵角色聊天），底層執行的還是使用者自己有權限、自己在用的同一套工具——不是把執行能力開放給一個原本不該有這個能力的新角色。

## 安全設計：不是「開放執行」，是「開放執行＋逐步確認」

**單純的 wake-word 直接執行是不可接受的**——語音轉文字誤判、`page-digest.js` 抓回來的任意網頁內容（理論上的提示詞注入來源）、使用者自己講錯話，都可能變成意外執行風險指令的管道。因此這個功能刻意做了三層邊界：

1. **不做真正的語音喚醒詞**：沿用既有的點擊錄音/打字流程觸發「進入 CLI 模式」這句話，不新增背景常駐麥克風——`docs/specs/0004` 已經因為聲學回授/幻覈輸入的問題拿掉過一次持續語音模式，這裡不重蹈覆轍（見該 spec 的「拿掉持續語音模式」段落）。
2. **只有 Read/Glob/Grep 自動放行，其餘一律經過確認**：`canUseTool` callback 攔下每一個非唯讀的工具呼叫（`Bash`、`Write`、`Edit`、`WebFetch`...），暫停執行、把操作內容組成一句人看得懂的文字，透過桌寵原本的文字泡泡＋語音回覆問使用者同意/拒絕，收到明確的「同意」才會真的放行。**不用 `bypassPermissions` 模式**——那等於把 wake-word 誤判的風險直接放大成「誤判就等於執行」。
3. **同意/拒絕判斷寧可含糊也不猜**：`interpretYesNo()` 看不懂使用者在說同意還是拒絕時回傳 `null`，桌寵會要求使用者換句話說，不會把模稜兩可的回覆偷偷當作同意——見 `claude-cli.js` 的測試案例。

## 已知還沒解決、刻意先不擋的風險（記錄下來，不是忽略）

- `page-digest.js` 抓回來的網頁內容，如果使用者在 CLI 模式下貼一個網址，理論上網頁內容可能包含試圖影響 Claude 行為的文字（提示詞注入）。目前沒有針對 CLI 模式做額外的內容過濾——跟一般聊天模式共用同一個「網址內容當上下文」的機制。因為所有非唯讀操作都還是要經過 `canUseTool` 確認，這道最後防線理論上仍然擋得住「網頁內容誘導執行破壞性指令」，但如果使用者對著確認提示不假思索地回答同意，這道防線就沒有意義——**這個功能的安全性最終還是依賴使用者自己在確認時真的有看清楚在同意什麼**，不是純技術手段能完全保證的事。
- CLI 模式的工作目錄固定在 repo 根目錄，沒有進一步限制 Claude 能不能碰到目錄以外的東西（例如 `additionalDirectories`／作業系統層級的檔案權限）——完全依賴 Claude Code 本身的邊界，桌寵這層沒有疊加額外的沙盒。

## 範圍界定：只換「觸發方式」，不換「誰在執行」

跟 ADR-0001（Ollama）那次「新增一個可選路徑，不動預設行為」的精神一致：CLI 模式是**額外的、需要使用者主動說出觸發短語才會進入**的模式，不會讓一般聊天無意間變成執行本機任務。退出方式同樣是明確的觸發短語，不是逾時自動退出（逾時退出反而可能讓使用者以為還在一般聊天、卻其實還處於會執行指令的狀態，更危險）。

# desktop-pet-web 手勢動作觸發只作用於頁面本地展示卡片、跟操控模式互斥、只做單一手勢

desktop-pet-web 高精度 3D 展示卡片（Aatrox3DShowcase）要新增「開鏡頭比手勢觸發角色動作」的功能。需求訪談過程中有三個真的有取捨、值得記錄的決定：範圍要不要橋接到真正的桌寵、要不要跟現有的操控模式（WASD）並存、要做幾種手勢對應。這份 ADR 記錄最後選了什麼、為什麼。

## 決定

1. **只作用在 Aatrox3DShowcase 卡片本身，完全不呼叫 `control-server.js`，不修改 `control-server.js` 或 `desktop-pet/main.js` 任何一行**。跟「本機控制面板」（同一頁面上遙控真正桌寵的既有按鈕）、「手勢拖曳」（Hero 區塊卡片上的另一種手勢功能，只搬動模型位置）是三個各自獨立的機制，即使桌寵沒有在跑、或 `control-server` 連不上，手勢動作觸發照常可用。
2. **手勢模式跟操控模式（WASD＋空白鍵）互斥**：一次只能開一種輸入方式，開啟其中一個會 disable 另一個的進入按鈕。
3. **只做一種手勢**（👍 `Thumb_Up`）**對應一種行為**（觸發下拉選單目前選定的動作，等同鏡頭版的空白鍵），不做第二種手勢對應其他動作。

## 為什麼不橋接到真正的桌寵

跟 `docs/adr/0011`（手勢拖曳）記錄的理由完全一致，這裡不重複展開，只列結論：座標系換算對這個功能沒有意義（鏡頭前比手勢，跟真正桌寵視窗在螢幕上的哪個位置無關）、`control-server` 現有端點是一次性 request/response，不是為即時手勢串流設計的、以及最重要的「失效隔離」——只作用在頁面本地卡片，鏡頭/WASM 出問題最壞就是「這張卡片的手勢模式不能用」，不會波及真正在跑的桌寵。

## 為什麼跟操控模式互斥，不讓兩者並存

需求訪談時列過「兩者並存」的方案（操控模式開啟時，WASD／空白鍵照舊，額外多一個手勢也能觸發），最後選擇互斥，理由：

1. **避免輸入來源互相干擾**：操控模式下使用者的手通常在鍵盤上打字/按 WASD，鏡頭同時開著容易把打字/按鍵的手部動作誤判成手勢，兩套輸入同時運作會增加意料之外的觸發。
2. **實作/測試量體對齊晚間項目的時間預算**：兩者並存需要處理「鍵盤觸發跟手勢觸發同時發生」的競態情境（例如同一幀又按空白鍵又比 👍），互斥模式下這個情境天生不存在，不需要額外設計/測試。
3. **兩者要展示的東西不衝突**：操控模式的賣點是「走位＋揮劍」，手勢模式的賣點是「用手隔空操控角色」，各自獨立展示反而各自更清楚，不需要合併成一個更複雜的複合模式。

## 為什麼只做一種手勢

MediaPipe `GestureRecognizer` 內建分類其實有好幾種（`Open_Palm`／`Closed_Fist`／`Victory`／`Thumb_Up`／`Thumb_Down`／`Pointing_Up`／`ILoveYou`），技術上要多對應幾種並不難。這次只做 👍 一種，理由：

1. **先求核心互動可靠、有清楚回饋，量體對齊晚間項目的 2-3 小時預算**——每多一種手勢，就要多一組提示文案／多一輪手動驗證，稀釋掉把「核心一種手勢要做到手感紮實」做好的時間。
2. **多種手勢對應多種動作，會需要使用者事先知道每種手勢對應什麼**，這是額外的認知負擔／UI 說明成本，不是這次要解的問題；單一手勢（比讚）語意直覺（「讚，來一下」），不需要額外教學。
3. **這是可以自然擴充的方向，不是關死的設計**——`AatroxGestureTrigger.tsx` 的邊緣觸發判定是照 `categoryName` 分支的，之後如果想加第二種手勢，是往既有結構裡加一個分支，不需要重新設計架構。

## 影響

- 不需要動 `control-server.js`／`main.js`，這次的實作範圍是 `desktop-pet-web` 內部（新增一個獨立元件 `AatroxGestureTrigger.tsx` + 對 `Aatrox3DShowcase.tsx` 的小幅擴充），跟桌寵 Electron App 完全解耦，複用 `gesture-drag/` 已經驗證過的 MediaPipe 載入慣例。
- 如果之後想要「操控模式跟手勢模式並存」或「多種手勢對應多種動作」，那是全新的一輪設計（競態處理、UI 說明、更多手動驗證），不是這次範圍的自然延伸，屆時應該另開 ADR 或修訂本篇，不要預設可以直接沿用這次的實作。

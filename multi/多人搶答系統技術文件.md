## 系統架構概覽

```
瀏覽器 host.html  ──┐
                    ├── MQTT Broker (WebSocket :9001) ──┬── 玩家 player.html (1~4 人)
Node-RED (選配) ────┘                                   └── Node-RED 音效觸發 (選配)
```

- **通訊協定**：MQTT over WebSocket（mqtt.js 瀏覽器端）
- **無需後端程式**：Broker（例如 Mosquitto）即為唯一伺服器
- **人數上限**：主持人 + 玩家共 5 人，其中玩家最多 4 人
- **網路需求**：所有裝置必須在同一區域網路（或可互連的網段）

### `multi/host.html` — 主持人端

**責任**：控制整場遊戲流程，是唯一的權威方（所有狀態以主持人為準）。

#### 主要狀態物件 `HS`

```js
HS = {
  myId, myName,           // 主持人識別碼與名稱
  phase,                  // 當前遊戲階段（見狀態機）
  players,                // { id → { name, score, color } }
  questions,              // 本局題目陣列（已洗牌）
  qIdx,                   // 目前題號（0-based）
  gameMode,               // 'all' 全員作答 | 'race' 搶答制
  playerAnswers,          // { id → 字母 }（all 模式）
  playerDeltas,           // { id → 得分 }（all 模式）
  answeredIds,            // Set，已作答玩家（all 模式）
  wrongIds,               // Set，已答錯玩家（race 模式）
  buzzer,                 // 本題搶答者 { id, name, letter, delta }
  reactionTimes,          // { id → [秒數, ...] }，反應時間記錄
}
```

#### 核心函式流程

```
init()
  └─ loadBankIndex() → mqttInit() → L2D.init()

startGame()
  └─ startQ(0)
       └─ startPrepare()   ← 顯示倒數
            └─ startAnswering()  ← 顯示題目、開始計時
                 └─ onAnswer() / onTimeout()
                      └─ showResult()
                           └─ showExpl()
                                └─ nextQ() → startQ(idx+1)
                                          or endGame()
```

#### 主持人特殊能力

- 主持人本身也是「玩家 1」，可直接點選選項 A/B/C/D 作答
- 大廳可上傳自訂 JSON 題庫、使用表單手動建題、或選擇 AI 生成題庫
- 遊戲結束後顯示**歷史成績**與**反應時間分析**（最快/最慢/平均）

### `multi/player.html` — 玩家端

**責任**：接收主持人廣播狀態、顯示題目與選項、發送作答、顯示個人結果。

#### 主要狀態物件 `PS`

```js
PS = {
  myId,          // sessionStorage 持久化的識別碼（重新整理不變）
  myName,        // 玩家名稱
  score,         // 當前分數
  localPhase,    // 玩家端目前顯示的 phase（避免重複處理同一 phase）
  clockOffset,   // 與主持人的時鐘差（ms），消除裝置時間不一致
  answered,      // 本題是否已作答
  myAnswer,      // 本題所選字母（供結果顯示圈叉用）
  prevScore,     // 作答前分數快照（計算 delta 用）
  gameMode,      // 同步自 STATE
}
```

#### 圈叉判斷邏輯（個人化結果）

結果顯示以「**自己的作答**」為準，不受他人影響：

```
iAnsweredCorrect = (PS.myAnswer === correctAnswer) → ⭕ 綠色
iAnsweredWrong   = (PS.myAnswer 存在 && 不等於正確答案) → ❌ 紅色
未作答 / 被鎖定   = → ⏰ 灰色
```

## 調整參數區（MP_CFG）

**位置**：`multiplay.js` 第 4–33 行，**改這裡即可影響整場遊戲**。

```js
const MP_CFG = {
  brokerIP:     window.location.hostname || '192.168.0.171',
  //  ^ MQTT Broker IP，預設自動跟隨頁面所在伺服器 IP
  //    若手動指定，請改為 Mosquitto 所在機器的 IP

  wsPort:       9001,
  //  ^ MQTT WebSocket 埠號，Mosquitto 預設為 9001
  //    需在 Mosquitto 設定檔中啟用 listener 9001 websockets

  QUESTION_BANK: '../questions/business.json',
  //  ^ 預設題庫路徑（主持人大廳可再動態切換）

  GAME_Q_COUNT: 10,
  //  ^ 預設每局題數（主持人大廳可修改，範圍 1–50）

  PREPARE_TIME: 3,
  //  ^ 準備倒數秒數（每題開始前的倒數，建議 3–5 秒）

  ANSWER_TIME:  12,
  //  ^ 每題作答秒數（計時器倒數，建議 10–20 秒）

  LOCK_MS:      900,
  //  ^ 搶答畫面停留時間（ms），讓玩家看清楚搶答者後才揭曉答案

  RESULT_MS:    2500,
  //  ^ 結果遮罩顯示時間（ms），顯示圈叉後停留多久才進入解說

  EXPL_MS:      4000,
  //  ^ 解說遮罩顯示時間（ms），顯示正確答案與說明後停留多久

  enableLive2D: true,
  //  ^ 玩家裝置是否載入 Live2D（true=載入，false=跳過，低效能裝置建議 false）

  MAX_SCORE:    10,
  //  ^ 立即作答答對的最高得分（建議與題數相符，使滿分 = 題數 × MAX_SCORE）

  MIN_SCORE:    1,
  //  ^ 最後一秒作答答對的最低得分

  MAX_PENALTY:  5,
  //  ^ 立即作答答錯的最高扣分

  MIN_PENALTY:  1,
  //  ^ 最後一秒作答答錯的最低扣分

  maxPlayerChars: 4,
  //  ^ 玩家端 join 畫面「角色數」選單最多開放到幾個（2~4）。手機等低效能裝置
  //    渲染越多角色越吃效能，調低即可讓玩家選單不出現 3/4；host.html 的角色數
  //    選單不受此值限制（主持端通常用自己電腦）

  IDLE_MOTION_MS:    6000,
  //  ^ Live2D 答題期間閒置循環的動作/表情觸發間隔（唯一控制點）

  HEARTBEAT_MS:      3000,
  //  ^ 玩家送出在線心跳的間隔；主持人端也用同一個數字當作輪詢檢查頻率

  OFFLINE_MS:        10000,
  //  ^ 主持人判定玩家離線的門檻（須明顯大於 HEARTBEAT_MS 留緩衝，避免正常網路抖動被誤判離線）

  TOAST_MS:          1600,
  //  ^ 得分飄字（showToast）顯示多久後自動消失

  MQTT_RECONNECT_MS: 3000,
  //  ^ MQTT 斷線後的自動重連間隔
};
```

> **注意**：修改後重新整理所有頁面才會生效。`MP_CFG` 是前端常數，不會自動同步。

## MQTT 主題對應表

| 主題 | 方向 | QoS | Retain | 用途 |
|------|------|-----|--------|------|
| `quiz/multi/join` | player → host | 1 | 否 | 玩家加入申請（含 id、name） |
| `quiz/multi/state` | host → all | 1 | **是** | 遊戲狀態廣播（phase、題目、選項、分數等） |
| `quiz/multi/answer` | player/host → host | 1 | 否 | 作答（含 id、name、letter） |
| `quiz/multi/result` | host → all | 1 | 否 | 本題結果（正確答案、得分、解說） |
| `quiz/multi/l2d` | host → all | 0 | 否 | Live2D 動作同步（說話、情緒） |
| `quiz/sound` | Node-RED → all | 0 | 否 | 音效觸發指令（純文字 track 名稱，選配） |

**Retain 說明**：`quiz/multi/state` 設定為 Retain，玩家晚加入時也能立即收到最新遊戲狀態。

## 遊戲流程與狀態機

### 主持人端 `HS.phase`

```
lobby
  │ 點擊「開始遊戲」
  ↓
prepare  ←── 每題開始（倒數 PREPARE_TIME 秒）
  │
  ↓
answering  ←── 顯示題目、計時 ANSWER_TIME 秒
  │ 所有人答完 / 時間到 / 搶答正確
  ↓
locked  ←── 停留 LOCK_MS ms（顯示搶答者）
  │
  ↓
result  ←── 顯示圈叉、更新分數，停留 RESULT_MS ms
  │
  ↓
expl  ←── 顯示正確答案與解說，停留 EXPL_MS ms
  │ 還有題目
  ↓ ──→ prepare（下一題）
  │ 全部結束
  ↓
end
  │ 點擊「再玩一次」
  ↓
lobby
```

### 玩家端收到 `STATE.phase` 的對應行為

| phase | 玩家畫面動作 |
|-------|------------|
| `lobby` | 返回加入畫面，重置分數 |
| `prepare` | 顯示倒數覆蓋層，隱藏選項 |
| `answering` | 顯示題目與 ABCD 選項，啟動計時器 |
| `locked` | 鎖定按鈕，若有搶答者顯示搶答提示 |
| `result` | 由 `RESULT` 訊息（而非 STATE）觸發，顯示圈叉 |
| `expl` | 顯示正確答案與解說 |
| `end` | 切換至結算畫面 |
| `host_left` | 返回加入畫面，顯示「主持人已離開」 |

### 唯一主持人保護

`host.html` 可能從三個不同管道被打開（VS Code Live Server 直接瀏覽、`host-app`、`launchers/啟動-網頁遊戲.bat`），這三個管道彼此的 `localStorage` 因為 origin 不同互不相通，但底層連的是**同一個 MQTT broker**，所以同一時間如果真的打開多份 `host.html`，會變成多個主持人搶著發布 `STATE`/`RESULT`，互相打架、玩家端畫面閃爍矛盾。

解法是拿 `STATE` 主題本身當唯一性判斷依據（不用額外開新主題），但**分成兩階段連線**，不是一條連線從頭用到尾：

### Phase 1：哨兵連線（不帶 will）

`mqttInit()` 一開始先開一條**刻意不帶 `will`** 的哨兵連線（`clientId: 'scout_...'`），訂閱 `STATE`（retained）並短暫等待（800ms）：
- 收到 retained 訊息，且 `phase` 不是 `'host_left'` → 判定已有主持人在跑 → 顯示全螢幕「已有主持人在運作中」擋版，哨兵連線直接丟棄。
- 沒收到訊息、或收到的剛好是 `'host_left'`（代表上一個主持人已經正常/異常離線）→ 判定可以安全接手，丟棄哨兵連線，進入 Phase 2。

### Phase 2：正式連線（帶 will），只有確定要當主持人才會開

```js
will: {
  topic: MP_TOPICS.STATE,
  payload: JSON.stringify({ phase: 'host_left' }),
  qos: 1,
  retain: true,   // 不管正常關閉、當機、斷電，STATE 都會被覆蓋成 host_left，
                   // 下一個嘗試開啟的 host.html 才能正確判斷「主持人已經不在了」
},
```

`resetToLobby()`（結算畫面「🏠 回大廳」）只發 `lobby`，不會借用 `host_left`——早期版本曾經多發一次非 retained 的
`host_left` 當「強制重置訊號」，但玩家端收到 `host_left` 一律會顯示「主持人已離開，請稍後重新加入...」並把畫面
強制切回加入畫面，導致主持人只是回大廳而已，停留在加入畫面／結算畫面的玩家卻被誤導成主持人斷線、畫面也多
被切換一次。`lobby` 訊息本身在玩家端 `case 'lobby'` 已經會把剛結束那局（`localPhase === 'end'`）或還沒加入的
玩家重置回加入畫面，不需要額外訊號。

### 為什麼要分兩階段連線，不能只用一條連線判斷完再決定要不要留著

這是**實測抓到的真實 bug**，過程分兩層：

1. **第一版**：只用一條帶 `will` 的連線，判斷完是「第二主持人」就呼叫 `end(true)` 強制斷線。強制斷線不會送出正常的 MQTT DISCONNECT 封包，broker 當成非正常斷線，**觸發這條連線自己的 will**，把 `host_left` 蓋成 retained，蓋掉真正主持人原本正確的 `STATE`——結果「擋人」這個動作本身把證據銷毀掉了，被擋住的分頁重新整理一次就能繞過去。
2. **第二版**：把 `end(true)` 改成 `end()`（正常斷線）修掉了上面那個情境，但問題的根本沒解決——**只要連線帶了 `will`，它在還沒確定自己是不是主持人之前，就是一顆不安全的地雷**。判斷過程中（訂閱 STATE、等 800ms）如果分頁被**快速連續重新整理**，瀏覽器來不及送出正常 DISCONNECT 就把分頁砍掉重載，broker 一樣把這條「還在判斷中」的連線當非正常斷線，一樣觸發它的 will，一樣蓋掉真正主持人的狀態。

`will` 是連線建立當下就決定好、之後改不了的東西，沒辦法「連線先不帶 will，判斷完之後才補上」。唯一乾淨的解法就是分成兩條連線：**哨兵連線全程不帶 will**（不管怎麼被粗暴中斷都不會誤觸發任何東西），只有確定要接手了，才開一條帶 will 的正式連線——這樣「還在判斷中」的階段完全不存在被快速重新整理繞過的風險。

**沒有「強制接管」機制**——只要偵測到的主持人還在，新開的 `host.html` 就會一路顯示擋版，唯一解除方式是原本那個主持人真的結束執行（正常關閉或斷線），不會因為等待逾時就自動放行。

## 遊戲模式說明

### 📋 全員作答制（`gameMode: 'all'`）

- 所有玩家（含主持人）均可作答
- **等所有人答完，或時間到**，才一次公布答案
- 先答並答對得分較高（線性縮放至剩餘秒數）
- 答錯扣分，未作答不扣分

### ⚡ 搶答制（`gameMode: 'race'`）

- 最快答對的玩家結束本題（其他人停止作答）
- 答錯者被排除在本題之外（加入 `wrongIds`），其餘人繼續作答
- 所有人均答錯或時間到 → 顯示「無人答對」

## 計分公式

**核心概念：越快答越多分，越慢答越少分。答錯也依速度扣分。**

計時器從 12 秒倒數，剩餘時間越多代表「越快答」，得分也越高；反之剩越少時間，得分越低。答錯同理，越快答錯扣越多。

```
得分 / 扣分依「剩餘時間佔總時間的比例」線性縮放：

  剩餘比例 = 剩餘秒數 ÷ 作答總秒數（介於 0 到 1 之間）

  答對得分 = 最高得分 × 剩餘比例（最少拿到最低得分）
  答錯扣分 = 最高扣分 × 剩餘比例（最少被扣最低扣分）
```

**白話舉例**（預設：作答時間 12 秒、答對最高 10 分、答錯最多扣 5 分）：

| 情境 | 剩餘時間 | 答對得分 | 答錯扣分 |
|------|----------|----------|----------|
| 題目一出來馬上按 | 12 秒（全部剩餘） | **+10 分** | −5 分 |
| 猶豫了一半時間 | 6 秒 | **+5 分** | −3 分 |
| 最後一秒才按 | 1 秒 | **+1 分** | −1 分 |
| 沒作答 | 0 秒 | 0 分 | 0 分 |

> **未作答不扣分**，只有主動按錯才會被扣。  
> **滿分計算**：若設 10 題、每題最高 10 分，完美全對可拿 100 分。

## 題庫格式規範

### JSON 陣列，每題一個物件

```json
[
  {
```

#### Ollama Base URL 的預設值會跟著開頁面的網址走

`#ollama-url` 欄位原本寫死 `http://127.0.0.1:11434`，只有「瀏覽器跟 Ollama 同一台機器」時才對；
這支頁面常常是遠端連過來用的（host 在另一台機器開瀏覽器連過來，或是內嵌在 `host.html` 裡從
別的裝置打開），這種情況下 `127.0.0.1` 永遠指向瀏覽器自己那台機器，連線必定失敗，卻容易被
誤會成「Ollama 沒開」或防火牆問題。`initOllamaUrlDefault()`（頁面 `Init` 區塊，`loadConfig()`
之前執行）跟 `multiplay.js` 的 `MP_CFG.brokerIP` 用同一招：抓開這個頁面當下的
`window.location` 當預設值，依連線方式分兩種情況（`_isPrivateLanHost()` 判斷）：

- **區網 IP**（`10.x`／`192.168.x`／`172.16-31.x`）：假設 Ollama 跟網站伺服器同一台機器，
  直連 `http://{該IP}:11434`；這條路需要 Ollama 開 `OLLAMA_HOST=0.0.0.0` 才收得到跨機連線
  （純區網，沒有經過 Caddy 反代）。
- **其他情況**（ngrok 網域等公網位址）：直連裸埠 11434 不可能成功——ngrok 只轉發它被要求
  轉發的那一個埠（這裡是 8080），改用下一節的 `/ollama-proxy` 反代路徑，值是
  `{頁面本身的 origin}/ollama-proxy`。

純本機開（`localhost`/`127.0.0.1`）維持 HTML 原本寫死的值不變動。使用者如果曾經手動存過
自訂網址（`localStorage['quiz_ai_config']`），`loadConfig()` 會照樣覆蓋這個自動預設值，
不會蓋掉使用者自己的選擇。

#### 讓公網（ngrok）也能連到 Ollama：`/ollama-proxy` 反代

單一個 ngrok tunnel 只轉發它被要求轉發的那一個埠（這個專案轉發給 Caddy 的 8080），Ollama
的 11434 埠不會自動一起被轉發出去——免費版 ngrok 通常一次只能掛一個 tunnel，另外開一條專門
給 11434 用不划算，也等於把 Ollama 整個裸露給公網。做法是讓 Ollama 流量「走同一個 8080、
換一個路徑」，跟 `/mqtt`、`/api/*` 同一套模式：`Caddyfile` 新增

```
handle_path /ollama-proxy/* {
    reverse_proxy localhost:11434 {
        header_up Host localhost:11434
        header_up -Origin
    }
}
```

`handle_path` 會把 `/ollama-proxy` 這段前綴砍掉才轉發，Ollama 收到的是 `/api/chat` 這種它自己
認得的路徑（不是 `/ollama-proxy/api/chat`，Ollama 沒有這個路徑會 404）。兩個 `header_up`
都是實測跑出來才補的，各自對應一種會被 Ollama 拒絕的情況：

- **`header_up Host localhost:11434`**：`reverse_proxy` 預設會把 client 原本打的 Host
  （例如 `xxx.ngrok-free.dev`）原封不動轉給後端，較新版 Ollama 會檢查收到的 Host header
  是不是合法本機位址，兜不上就直接回 **403**（防 DNS rebinding 攻擊的機制，不是「跨機
  連線」被擋，是 Host header 對不上被擋）。沒有這行，`GET /api/tags`（測試連線／列模型）
  也會一起被擋。
- **`header_up -Origin`**：瀏覽器對「非簡單請求」（POST 帶 `Content-Type: application/json`
  這種）會夾帶 `Origin` header，**即使頁面跟目標網址同源也一樣會送**；`GET /api/tags`
  屬於簡單請求，瀏覽器不會夾帶 Origin，所以只補 Host 那行時「測試連線」看起來完全正常
  （能列出模型），只有真正按下生成、送出 `POST /api/chat` 才會踩到——Ollama 的
  `OLLAMA_ORIGINS` 允許清單預設只認 `localhost` 那幾種模式，ngrok 網域對不上，一樣回
  403。這裡直接把 `Origin` 這個 header 砍掉（`-` 前綴是 Caddy 移除 header 的語法），
  讓 Ollama 收到的請求跟根本沒帶 Origin 的請求同等待遇，不用另外去猜 `OLLAMA_ORIGINS`
  該填什麼值才會通過。**只修 Host 沒修 Origin 會出現「測試連線成功、按生成卻 403」這種
  容易誤判成別的原因的現象，兩個都要補才行。**

因為 Caddy 本身跟 Ollama 是同一台機器互連（`localhost:11434`，真正的 loopback），這條路
**不需要**在 Ollama 那邊設定 `OLLAMA_HOST=0.0.0.0`（不是跨機連線）——比直連 11434 的區網
做法還簡單，Ollama 完全不用改設定，只要正常跑著就行；`OLLAMA_ORIGINS` 也不需要另外設定，
上面 `header_up -Origin` 已經在 Caddy 這層處理掉了。

前端配合的地方：`_normalizeOllamaUrl()` 原本會把使用者填的網址整個簡化成 `origin`（砍掉路徑），
這樣會把 `/ollama-proxy` 這段路由用的路徑前綴也砍掉，改成只砍掉使用者常見手滑多打的
`/api` 尾巴（Ollama 官方文件範例常這樣寫），其餘路徑原樣保留。`testOllamaConnection()` 的
連線失敗提示也拆成兩種文案：偵測到 base URL 是「頁面同源 + `/ollama-proxy`」時顯示反代相關
的排查項目，不會誤導使用者去設定根本不需要的 `OLLAMA_HOST`／`OLLAMA_ORIGINS`。

**Caddyfile 改了要讓已經在跑的 Caddy 重新載入才會生效**：`caddy.exe run` 不會自動偵測檔案
變動，改完 `Caddyfile` 要嘛重開那個視窗，要嘛在專案根目錄下 `caddy.exe reload` 熱重載。

實測方式：另外開一個 admin API 關閉、埠號不同的 Caddy 測試實例（避免跟本機真正在跑的那個
搶 `127.0.0.1:2019` 這個 Caddy admin 埠），確認 `curl http://127.0.0.1:{測試埠}/ollama-proxy/api/tags`
真的能拿到本機 Ollama 的模型清單；瀏覽器端用 Chromium 的 `--host-resolver-rules` 把一個假網域
指向 `127.0.0.1`，模擬「從公網網域開這個頁面」的情境。**這裡有個教訓**：一開始只測了
「測試連線」（`GET /api/tags`）就以為修好了，`curl` 直接測 `POST /api/chat` 也正常（curl
不會像瀏覽器一樣自動夾帶 `Origin` header），兩邊都測成功，實際上漏了 `Origin` 那個問題——
真正按「開始生成」的按鈕（瀏覽器送出真正的 `POST /api/chat`）才 403。之後補上「用瀏覽器點
生成按鈕跑完整流程」這一步才抓到，單測 API 端點、用 curl 測都不能取代「模擬真實使用者操作
路徑」的整合測試。

#### AI 生成漏填 domain 時的保底補值

OpenAI 走 `strict:true` 的 `json_schema`（structured outputs），`domain` 幾乎保證會填；Ollama
只有 `format:'json'`（保證合法 JSON，不保證欄位齊全），本機模型能力較弱時，就算
`SYSTEM_PROMPT` 已經明講必填，還是可能漏掉某幾題的 `domain`——這幾題進了遊戲的學習報告會被
歸進「(未分類)」，沒辦法做「常錯範圍」分析。`normalizeQuestionDomains()` 在 AJV 驗證之前
先補一層：漏填的題目退回使用者填的「題庫名稱」欄位當 `domain`（至少還跟這份教材主題有關，
比完全沒有 domain 好）；使用者沒填題庫名稱就維持留空，遊戲端本來就有 `(未分類)` 的顯示邏輯
接住。

#### 遠端連線時，生成完的三顆匯出按鈕都測過

「💾 下載 JSON」「🎮 直接匯入遊戲系統」「💾 存入題庫（永久）」這三顆按鈕串接方式不同，遠端
（公網 ngrok 網域）存取時的風險也不一樣，逐一確認過：

- **下載 JSON**：純前端 `Blob` + `<a download>`，完全不碰伺服器，跟連線方式無關，一定能用。
- **直接匯入遊戲系統**：寫進 `localStorage['quiz_ai_bank']`，`host.html` 靠 `storage` 事件
  即時偵測更新大廳題庫選單（見上面「AI 生成」那節）。這支頁面是用**相對路徑**當 iframe
  `src`（`openAIGenModal()` 設 `frame.src = '../ai-quiz-generator/index.html'`），不管
  `host.html` 本身是用 `localhost`、區網 IP 還是 ngrok 網域開的，iframe 都會落在同一個
  origin，`localStorage` 自然共用，不用額外處理。
- **存入題庫（永久）**：`savePermanentToProject()` 打 `fetch('/api/save-bank', ...)`，相對路徑
  一樣跟著頁面 origin 走，遠端連線時會經過 `Caddyfile` 既有的 `reverse_proxy /api/* localhost:8081`
  （這條路徑在加 `/ollama-proxy` 之前就存在，本來就支援公網）。後端 `handleSaveBank()`
  （`launchers/serve-lan.js`）沒有任何 Host／Origin 檢查，不會像 Ollama 那樣需要額外處理
  header，直接能用。

**實測方式**：另開一組獨立的 Caddy + 題庫寫檔 API 測試實例（不同埠號，不影響本機真正在跑
的那組），瀏覽器模擬公網網域開 `host.html`、開 AI 生成器彈窗、真的用 Ollama 生成一題、依序
按過三顆按鈕，確認：下載事件正確觸發且檔名正確；`localStorage` 正確寫入，且大廳的題庫下拉
選單即時多出對應選項（`🤖 {題庫名}`）；`/api/save-bank` 正確回應、題庫真的寫進
`questions/`、大廳選單也刷新出現存檔後的題庫名稱。全部正常，不需要額外修改。

### 題目範圍標記（`domain` 欄位）與學習報告

每題可選填 `domain` 欄位（自建題庫表單即 `#ed-domain`，上傳/AI 生成的題庫看檔案本身有沒有帶），
標記這題屬於哪個細項範圍（例如「會計學」題庫底下可以再細分「綜合損益」「資產負債表」）。
遊戲進行中會依這個欄位累計每個玩家的對錯，場末（`endGame()` → `sendStatsReports()`）
把每個玩家這場「哪個範圍答對/答錯幾題、具體錯在哪幾題」POST 給 `launchers/serve-lan.js`
的 `POST /api/record-session`，寫進 `stats/<暱稱>.json`（append-only，最近 200 場）。

大廳「題庫選擇」區塊的「📊 學習報告」按鈕開啟查詢彈窗（`openStatsModal()`），依暱稱查詢
`GET /api/stats?name=`，在前端把跨場次的 `sessions` 算成三個區塊：常錯範圍（依準確率排序）、
常錯題目（依出現次數排序）、歷次表現（逐場正確率）。`GET /api/stats-list` 給暱稱下拉選單用。

`player.html`（玩家端）的結算畫面、加入畫面都有同一顆「📊 學習報告」按鈕，跟 `host.html` 是
完全同一套彈窗 HTML／CSS／JS（含 `_renderDomainSection()` 等三個區塊的算法），只是預設帶入的
暱稱换成 `PS.myName`（還沒加入的話退回 `localStorage['quiz_pname']` 記住的上次暱稱），讓玩家
自己也能查自己的學習報告，不用借主持人的畫面看。兩份檔案各自維護一份重複的程式碼（沒有共用
模組），改其中一份記得另一份也要同步改。

彈窗 `#stats-modal` 的 z-index 刻意設成 `999999`——高於專案裡目前找得到的所有浮動元素
（Live2D 拖曳 canvas 9999、聊天/表情/語音廣播面板 10000~10002、賽前閒聊角標 99999、主持人
搶佔擋版 99999……），確保不管當下疊了什麼面板，學習報告一開永遠蓋在最上面，右上角 ✕ 一定
點得到。

暱稱即識別碼，沒有帳號驗證——跟 `/api/save-bank` 同一套信任模型（見下方「公網開放時的
寫檔面」），公網開放時任何人理論上可以用別人的暱稱寫入/查詢假資料。`stats/` 目錄已加進
`.gitignore`（使用者個人作答資料，不進版本控制）。

#### 分類篩選（題庫 `category`，跟每題 `domain` 是兩層不同粒度）

「管理題庫」彈窗（`openBankMgrModal()`）能替每個題庫設定 `category` 欄位（`questions/index.json`
的 `category`），把「相關」的題庫歸成同一組——例如 `資產負債.json`／`綜合損益.json`／
`機會成本.json` 都歸進「會計學」。這是題庫「之間」怎麼分群，跟每題的 `domain`（題庫「裡面」
再細分範圍，例如「會計學」底下的「綜合損益」）是不同粒度、不衝突。目前各題庫的分類：

| 題庫 | 分類 |
|------|------|
| `資產負債.json`／`綜合損益.json`／`機會成本.json` | 會計學 |
| `business.json` | 商業管理 |
| `security.json` | 資訊安全 |
| `ai.json` | 人工智慧 |
| `english.json` | 英文 |
| `questions.json` | ESP32 硬體 |
| `豐之優露營區_50題.json` | 營隊活動 |

學習報告彈窗查到某暱稱的所有場次後，會抓 `questions/index.json` 建一份 `bankFile → category`
對照表（`_ensureBankCategoryMap()`，惰性抓一次、快取著），依這份場次「實際出現過」的分類
（`_renderStatsCategoryOptions()`）動態長出分類下拉選單——沒分類的題庫、這個人沒打過的分類都
不會出現在選單裡。選了分類之後，`renderStatsReport()` 把常錯範圍、常錯題目、歷次表現三個
區塊都套用同一份篩選後的場次（不是只篩「常錯」兩塊，歷次表現卻還混著別分類的場次，會很怪）；
選「全部分類」則不篩選，回到原本行為。這一層篩選完全是前端算的，後端 `/api/stats` 不用跟著
改。

#### 面板成長（題庫、常錯題目只會愈養愈多）的因應

常錯範圍、常錯題目、歷次表現三個區塊改成不設筆數上限（原本常錯題目砍在前 15 題，題庫一多
就看不到其他錯題），改成各自包一層固定高度、可獨立捲動的內框（`.stats-domain-list`／
`.stats-wrong-list`／`.stats-session-scroll`，都是 `max-height` + `overflow-y:auto`），資料
再怎麼長都裝得下，也不會把整張卡片、甚至整個彈窗越撐越高。跟外層 `.stats-scroll-body`（整
個彈窗本身的捲動）是「外層保底、內層各自再捲一層」，兩層互不衝突。

#### 常錯範圍的自動配色（domain → 顏色）

「常錯範圍」每個 domain 名稱前有一個色點（`.stats-domain-dot`），顏色靠
`_buildDomainColorMap(sessions)` 決定：把這次篩選範圍內出現過的所有 domain 依字母序排好，
依序從 `_DOMAIN_COLOR_PALETTE`（12 色固定調色盤）發色，同一次渲染裡 domain 數只要不超過
12 個就保證互不撞色；超過 12 個才會循環重複。這個對照表只在單次 `renderStatsReport()` 呼叫
裡有效（不是全域固定配色），所以同一個 domain 換一個分類篩選、換一批 sessions 時顏色可能
不一樣。新增題庫、新增 domain 完全不用手動維護配色表——`_buildDomainColorMap()` 收到的
domain 清單本來就是動態算出來的，新 domain 自然會排進去、拿到調色盤裡還沒被佔用的顏色，
「自動套用新顏色」是這個機制天生的行為，不是另外寫的特例。

「常錯題目」單純列出出現次數（`錯 N 次`），沒有長條也沒有套用這份配色——數字本身已經夠
直觀，跟「常錯範圍」需要看「準確率高低」的長條不是同一種需求，加了反而是多餘的視覺噪音。

#### 常錯題目可展開看正解與解說

原本的學習報告只停在「診斷」層——告訴玩家哪裡常錯、錯幾次，但沒說正確答案是什麼、為什麼，
玩家想學到東西還是得等下一次被考到同一題。`host.html` 的 `onAnswer()` 答錯時，除了原本的
`yourAnswer`/`correctAnswer`（字母），額外從 `q.options` 記下對應的選項文字
（`yourAnswerText`/`correctAnswerText`）跟 `q.explanation`，隨 `sendStatsReports()` 一起送給
`launchers/serve-lan.js` 的 `POST /api/record-session`；後端 `handleRecordSession()` 的
`wrongQuestions` 白名單也跟著加了這三個欄位（`correctAnswerText`／`yourAnswerText` 各裁切
120 字、`explanation` 裁切 400 字，跟其他欄位一樣做長度上限）。

前端 `_renderWrongQuestionsSection()` 把同一題目跨場次合併計數時，一併把這三個欄位帶上
（任一場次有值就補齊，同一題的正解理論上每場都一樣，用「補齊」比「只取第一筆」更保險，
避免第一筆剛好是舊資料時整題都顯示不出來）。有存到正解/解說的題目，標頭列右側會多一個
可點的箭頭（`▸`/`▾`），點下去收合/展開一段「✅ 正解：X．選項文字」＋解說文字；**這個功能
上線前**錄的舊場次（`correctAnswerText`/`explanation` 都是空字串）沒有這幾個欄位，那些題目
就只顯示標頭列、不能展開，是正常的資料落差，不是 bug。

#### 常錯範圍的趨勢折線（有沒有在進步）

「常錯範圍」原本只呈現整段篩選期間的總平均準確率，看不出「這陣子是不是在進步」。
`_domainTrendPoints(sessions, domain)` 把 `sessions`（`/api/stats` 回來的場次，後端
append-only 寫入，順序本來就是舊→新）依序取出每一場「這個 domain 的準確率」，餵給
`_renderTrendSpark()` 畫成一個 60×20px 的 SVG 折線，塞進 domain 名稱後面固定寬度的
`.stats-domain-spark-wrap`（沒有畫折線時维持空白但保留寬度，各列版面才不會因為有沒有折線
而參差不齊）。折線顏色依「最後一場 vs 第一場」的差距判斷：進步超過 8 個百分點畫綠色
（`var(--green)`）、退步超過 8 個百分點畫紅色（`var(--red)`），介於中間就用 `_domainColor()`
的識別色——8% 只是「看得出差異、又不會太敏感」的經驗值，不是嚴謹的統計顯著性檢定。場次
少於兩筆（畫不出「趨勢」）就不畫折線，滑鼠移上去有 `<title>` 原生 tooltip 顯示「近 N 場：
X% → Y%」。

#### 對最弱範圍一鍵推薦題庫

`_renderDomainSection()` 的 `rows` 已經依準確率由低到高排序，`rows[0]` 就是目前篩選範圍內
最弱的 domain。玩家端額外在區塊最下面加一顆 `.stats-recommend-cta` 按鈕（「🎯 推薦主持人
多出「XX」」），從 `sessions` 裡反向找「最近一場包含這個 domain」的場次，取它的
`bankFile`/`bankName` 當推薦目標，呼叫上面「推薦題庫給主持人」那節的 `recommendBank()`——
把「發現弱點」跟「主動練習」串成一個動作，不用先關掉學習報告、再手動切去「有哪些題庫可選」
彈窗找同一個題庫。這顆按鈕只在 `player.html` 出現：判斷式是 `typeof recommendBank ===
'function'`，`host.html` 沒有定義這個函式（主持人看自己的報告，沒有「推薦給誰」的對象），
同一份 `_renderDomainSection()` 程式碼在兩邊執行時自然就不會長出這顆按鈕，不用另外傳參數
區分。

### 玩家端「📚 有哪些題庫可選？」彈窗

大廳的「📚 目前題庫」橫幅只顯示主持人*目前*選了哪一個，玩家看不到還有哪些題庫可以選、無從
預期接下來可能考什麼範圍。`player.html` 加入畫面新增「📚 有哪些題庫可選？」按鈕
（`openBankListModal()`），開啟 `#bank-list-modal` 清單，直接讀 `questions/index.json`
依 `category` 分組列出所有題庫的顯示名稱（沒有分類的排最前面，用「未分類」當群組標題）。
玩家不能真的切換題庫（那個操作只有主持人在 `host.html` 的下拉選單才做得到），但可以點清單
裡的題庫名稱「推薦」給主持人參考，見下一節。

這份清單不快取，每次開彈窗都重新 fetch 一次——內容不常變，快取與否差異不大，重抓可以確保
主持人剛上傳的新題庫（`/api/save-bank`）馬上就看得到，不用等玩家重整頁面。跟學習報告彈窗一樣
掛在 `<body>` 最外層、z-index 999999（見上面「學習報告」的 z-index 說明，同一套理由）。

#### 推薦題庫給主持人（`MP_TOPICS.BANK_RECOMMEND`）

點「可選題庫」清單裡的任一題庫，`recommendBank(bankFile, bankName)` 會發一則 MQTT 訊息到
新增的 `quiz/bank/recommend` topic（`multiplay.js` 的 `MP_TOPICS.BANK_RECOMMEND`），payload
`{ id, name, bankFile, bankName }`，`name` 取 `PS.myName`（還沒加入的話退回
`localStorage['quiz_pname']`，跟學習報告彈窗預填暱稱同一套邏輯，所以**加入房間前**就能推薦）。
單向 player → host、qos 0（跟 CHAT/DANMAKU 同等級的即時提示，不需要 retained、也不用玩家自己
收）。player 端點下去後本機立刻用既有的 `showToast()` 顯示「已推薦「XX」」當作送出成功的回饋；
MQTT 還沒連上時（`!PS.client || !PS.ok`）改顯示「連線中，稍後再試」，不會假裝送出成功。

`host.html` 在既有的 qos:0 訂閱清單裡加上這個 topic，收到後用 `showBankRecommendToast()`
顯示「💡 ${玩家名} 推薦「${題庫名}」」提醒主持人——純提示，**不會自動切換題庫**，主持人要
自己去「題庫選擇」下拉選單手動換，職責跟資料流向都刻意分開（玩家沒有寫入題庫狀態的權限）。

**沒有直接用既有的 `showToast()`**：那個函式（`.score-toast`）是設計給「同一時間只會有一則」
的場景用的（得分飄字、玩家上線/離線通知），固定畫在畫面正中央同一個座標——好幾個玩家幾乎
同時推薦題庫時，多則 `.score-toast` 疊在同一個座標會直接疊字看不清楚。改用
`showBankRecommendToast()`：訊息疊進 `#bank-recommend-stack`（畫面上方置中、`flex-direction:
column` 的容器），每則通知是容器裡一般的文件流子元素，新進來的自然排在下面，不會互相蓋住；
同時最多留 `BANK_RECOMMEND_MAX_VISIBLE`（7，依畫面高度抓的行數）則，超過就把最舊的（最上面
那列）直接移除、新的補在最下面，等於「從第一列開始覆蓋」，避免極端情況（很多人連續猛點）
把畫面塞滿。

`.bank-recommend-toast` 本身的文字樣式**刻意做成跟 `.score-toast` 同一種「發光飄字」風格**
（無背景框、粗體、色彩光暈），只是拿掉了「固定畫在畫面正中央」這個會疊字的定位方式，改放進
上面說的 `#bank-recommend-stack` 直排容器——純粹解決版面疊字問題，不改變原本的文字外觀。
顏色特意用**綠色**（`var(--green)`，跟 `.score-toast.pos` 同一色）而不是青色：整體畫面偏藍，
青色字在藍底上不夠跳，綠色對比更明顯，一眼就認得出「有新推薦」；字級也比一般提示文字略大
（1.5em）加強視覺重量。

## Live2D 整合說明

### 角色設定（`live2d.js` 頂部 `L2D_CFG`）

每個頁面在 `init()` 時設定 `L2D_CFG.storageNS`：

- 主持人端：`L2D_CFG.storageNS = 'h'`
- 玩家端：`L2D_CFG.storageNS = 'p'`

角色位置存入 `localStorage`，Key 格式為 `l2d_pos_{ns}_c1` / `l2d_pos_{ns}_c2`。

### 大廳角色選單（`../live2d_my_like/`，僅主持人本機）

大廳畫面「Live2D 角色」區塊有兩個下拉選單，列出 `live2d_my_like/config/manifest.json` 收藏庫裡的所有模型，選了之後存進 `localStorage`（`l2d_mylike_char1` / `l2d_mylike_char2`），重新整理頁面時 `init()` 會用它覆蓋 `L2D_CFG.char1.model` / `char2.model`。**只影響主持人自己的瀏覽器，不會同步給玩家**（玩家端固定用 `lib/live2d.js` 原本寫死的角色）。詳見 [live2d_my_like/config/模型收藏庫設定說明.md](../live2d_my_like/config/模型收藏庫設定說明.md)。

### 左下角懸浮控制按鈕

角色拖曳鈕原本是每個角色疊一顆獨立按鈕（`⠿` bottom:8/61/114/167px），角色數選到 3、4 時
會往上蓋到音效/BGM/特效這些固定位置的按鈕。改成收合式選單（見 `lib/live2d.js`
`_initDragButtons()`）：平時只有一顆骰子主按鈕，點下去才橫向展開，選完自動收合，
所以角色拖曳鈕永遠只佔 `bottom:8px` 這一格，下面這些固定按鈕才能整組往下補位一格：

| 按鈕 | 功能 |
|------|------|
| `🎲`（bottom:8px） | 拖曳角色選單主按鈕，點擊展開/收合下方各角色按鈕 |
| 展開後橫向排開的骰子點數按鈕 | 拖曳角色一/二/三/四（依角色數而定，1~4 點對應順位），選完自動收合 |
| `🔇`（bottom:61px） | 開關音效 |
| 音量滑桿（bottom:114px） | 調整 BGM 音量 |
| `⚡`（bottom:217px） | 開關攻擊特效（`MagicShotVFX`） |

**啟用拖曳時**：canvas 提升至 z-index:9999（蓋過所有 UI），可拖曳位置、雙指縮放、Shift+滾輪旋轉。  
**取消拖曳後**：canvas 恢復 z-index:5，遊戲 UI 正常互動。

### 主持人廣播 L2D 動作（玩家端同步）

主持人播放的情緒、說話動作會透過 `quiz/multi/l2d` 主題廣播，玩家端 `onL2DCmd()` 接收後同步執行，讓雙方角色反應一致。

### 不想啟用 Live2D

在 `MP_CFG` 設定 `enableLive2D: false`，玩家端不載入 Live2D 腳本，效能較低的行動裝置建議關閉。

## 使用說明（快速上手）

### 環境需求

- **MQTT Broker**：Mosquitto（或其他支援 WebSocket 的 Broker）
- **WebSocket 埠**：預設 9001（需在 Mosquitto 設定中啟用）
- **Web 伺服器**：提供 HTML/JS 靜態檔案（Node.js http-server、nginx、Python http.server 均可）
- **網路**：所有裝置須在同一局域網路

### 步驟一：設定 Mosquitto

`mosquitto.conf` 最低需求：
```
listener 1883
listener 9001
protocol websockets
allow_anonymous true
```

### 步驟二：啟動靜態伺服器

```bash
# 在 c:\question 目錄下
npx http-server -p 8080
# 或
python -m http.server 8080
```

### 步驟三：主持人開啟大廳

瀏覽器前往：`http://{主機IP}:8080/multi/host.html`

1. 輸入主持人名稱
2. 選擇遊戲模式（全員作答 / 搶答制）
3. 設定每局題數
4. 選擇題庫
5. 等待玩家加入（最多 4 人）

### 步驟四：玩家掃描 QR Code 加入

- 掃描大廳頁面的 QR Code，或手動開啟：`http://{主機IP}:8080/multi/player.html`
- 輸入名稱後點擊「加入」

### 步驟五：開始遊戲

- 至少 1 位玩家加入後，「開始遊戲」按鈕解鎖
- 主持人點擊「開始遊戲」，所有裝置同步進入遊戲

### 步驟六：遊戲結束後

- 結算畫面顯示名次、分數、歷史紀錄、反應時間分析
- 點擊「再玩一局」回到大廳重置分數，玩家自動重新加入

## 公網對外開放（ngrok + Caddy）

讓**區網外**（非同一 Wi-Fi/網段）的玩家也能加入遊戲。核心作法：用 [Caddy](../Caddyfile) 當本機網站伺服器 + MQTT 反向代理，再用 ngrok 把 Caddy 的對外連接埠曝露到公網。

### 為什麼可以不改任何程式碼

[`Caddyfile`](../Caddyfile) 除了當靜態網頁伺服器（`:8080`），還把 `/mqtt` 路徑反向代理到 `localhost:9001`（MQTT broker 的 WebSocket 埠）：

```
:8080 {
    root * .
    file_server
    reverse_proxy /mqtt localhost:9001 {
        transport http { versions 1.1 }
    }
}
```

而 `multiplay.js` 的 `mpMqttUrl()`（第 39–43 行）會依頁面協定自動切換連線方式：

```js
function mpMqttUrl() {
  if (location.protocol === 'https:')
    return `wss://${MP_CFG.brokerIP}/mqtt`;          // 走 Caddy 的 /mqtt 代理（公網用）
  return `ws://${MP_CFG.brokerIP}:${MP_CFG.wsPort}`; // 區網內直連 9001（本機用）
}
```

玩家透過 ngrok 的 `https://` 網址進來時，頁面協定是 `https:`，前端會自動改用 `wss://.../mqtt`，剛好對上 Caddy 的代理路徑 —— 不需要額外設定。

### 本機服務架構

公網對外開放時，主機端會同時跑下列本機服務，彼此只在「同一個 MQTT broker」這個點上匯合，網路路徑互不干擾：

| 服務 | Port | 用途 | 誰會連 |
|---|---|---|---|
| MQTT Broker（Mosquitto） | 9001 | 所有訊息真正的匯合點 | 以下兩者都連到它 |
| 5500 埠的靜態伺服器（VS Code Live Server，或 `serve-lan.js` 內建退路） | 5500 | 主持人本機開 `host.html`（`host-app` 桌面殼層也是走這個） | 只有主持人，純區網內 `http:` 直連 broker `ws://127.0.0.1:9001` |
| Caddy + ngrok | 8080 | 玩家端 `player.html`，含 `/mqtt` 反代 | 區網外玩家，走 `https:` → `wss://.../mqtt` |
| 題庫寫檔後端（`serve-lan.js` 8081 埠） | 8081 | `host.html` 上傳自訂題庫時 `POST /api/save-bank`，經 Caddy `reverse_proxy /api/* localhost:8081` 進來 | 只有主持人（走 `host.html` 上傳題庫時）|

> **公網開放時的寫檔面**：`/api/save-bank` 經 ngrok 也會對外可達（Caddy 代理模式下無法用來源 IP 區分，因為所有請求都從本機代理進來）。已做的防護：只接受 JSON 陣列題庫、題目數 1~1000、單檔 ≤512KB、請求 body ≤1MB、檔名 slug 化且不得跳出 `questions/`、內建題庫自動加 `custom_` 前綴不被覆寫、只能寫不能讀。最壞情況是外部玩家塞一些 `custom_*.json` 進 `questions/` 並在下拉選單多出幾筆——不會覆寫既有題庫、不會外洩檔案。真的在意就開放結束後清一下 `questions/` 跟 `index.json`。
>
> 同一套風險也適用於學習報告的三個 API（`/api/record-session`、`/api/stats`、`/api/stats-list`）：暱稱即識別碼、沒有帳號驗證，公網開放時任何人都能用別人的暱稱寫入假紀錄或查詢別人的學習報告。寫入端已限制單筆請求 ≤16KB、每個暱稱最多留 200 場紀錄，最壞情況是 `stats/` 底下多幾筆假資料或被人看到某暱稱的答題紀錄，不會影響題庫或遊戲本身。真的在意就開放結束後清一下 `stats/`。

> **`host-app`（Electron 桌面殼層）不受公網開放影響**：它固定載入本機 `http://127.0.0.1:5500/multi/host.html`，協定是 `http:`，永遠走區網內直連 `ws://127.0.0.1:9001`，跟 ngrok/Caddy 是否啟動完全無關。
>
> **不用再手動去 VS Code 按「Go Live」**：`launchers/啟動-主持人App.bat` 會先偵測 127.0.0.1:5500 有沒有人在聽——偵測到（不管是 VS Code Live Server 還是其他方式）就直接沿用；偵測不到的話，改用跟 `launchers/啟動-網頁遊戲.bat` 同一支內建的零套件相依 Node 靜態伺服器（`launchers/serve-lan.js`，設 `PORT=5500` 啟動），跟 VS Code 完全無關，服務內容一樣（同一支腳本，把整個專案根目錄當網站根目錄）。VS Code Live Server 仍然可以照用——如果 5500 已經有東西在聽，這個批次檔就不會另外啟動一個。

> **題庫寫檔 API（8081 埠）啟動時的畫面訊息**：這支視窗印的訊息會依「有沒有偵測到 `caddy.exe`」動態切換，不是寫死的——有偵測到（代表這支是搭配 Caddy 跑的小幫手，Caddy 本身在另一個視窗服務 8080 主要流量）會明講「非退路模式」，還會另外問一次 ngrok 本機的檢視 API（`127.0.0.1:4040`）有沒有指向 8080 的通道，查得到就把公網網址直接印出來（`[serve-lan] 偵測到 ngrok 通道，目前是公網模式：https://xxx.ngrok-free.dev`），不用再自己開瀏覽器查 `127.0.0.1:4040`。這個查詢非阻塞、1.5 秒逾時、查不到只代表「現在這一刻還沒查到」（ngrok 可能比這支腳本晚啟動），不代表沒有公網模式，訊息措辭上有照實區分「還沒偵測到」跟「確定沒有」。早期版本這行訊息不分情境、永遠印「這是沒偵測到 caddy.exe 時的退路版本」，即使在 Caddy 模式下也一樣，曾經讓人誤以為退回區網模式，已修正。

### 設定步驟（含實際指令）

這台機器的 Mosquitto 是裝成 **Windows 服務**，開機通常已在背景執行；ngrok 也已在本機完成 `authtoken` 登入，不用重新設定。

**1. 確認 MQTT broker（Mosquitto 服務）是否在跑**

```bat
sc query mosquitto
```

看到 `STATE : 4 RUNNING` 即可略過下一步；若是 `STOPPED`，用系統管理員權限的終端機啟動：

```bat
net start mosquitto
```

**2. 啟動 Caddy**（另開一個終端機視窗，會佔用前景，關閉視窗即停止）

```bash
cd c:\question
.\caddy.exe run
```

**3. 啟動 ngrok，對準 Caddy 的 8080**（再另開一個終端機視窗；⚠️ 不是對準 Live Server 的 5500——Live Server 沒有 `/mqtt` 反代路徑，遠端玩家會連不到 broker，搶答功能整個失效）

```bash
ngrok http 8080
```

**4. 取得公開網址**

`host.html` 大廳的「玩家加入網址」欄位與 QR code 會**自動偵測**：每 5 秒問一次
`GET /api/public-url`（`launchers/serve-lan.js` 的 `handlePublicUrl()`，不管是被 Caddy
的 `reverse_proxy /api/* localhost:8081` 轉進來，還是 `host-app` 自己在 5500 埠跑的那份
`serve-lan.js` 直接處理，都是同一支檔案、同一條路由），查到指向 8080 的通道就直接把
QR／連結換成 `https://xxx.ngrok-free.app/multi/player.html`，畫面上會多顯示一個
「🌐 已偵測到公網網址（ngrok）」的小標籤。這一步之所以不能沿用區網模式「只換
hostname」那套邏輯（`buildPlayerUrl()` 原本的 `if (host==='localhost') host = ip` 判斷）：
`host.html` 通常是用 `http://localhost:8080`（或 `127.0.0.1:5500`）開的，`location` 本身
不知道外面還套了一層 ngrok，protocol／port 都對不上（ngrok 走預設 443/https，不是本機
這裡的 8080/http，硬套只換 hostname 的邏輯會拼出打不通的網址），所以偵測到公網網址時
是整個網址直接用 ngrok 回報的 `public_url` 蓋過去，不是替換 hostname。

沒偵測到（ngrok 還沒啟動，或不是走 Caddy／`serve-lan.js`，例如純用 VS Code Live Server
開）就會照舊 fallback 回區網邏輯，不影響原本可用的功能；也可以自己手動查：

```bash
curl -s http://127.0.0.1:4040/api/tunnels | grep -o "https://[a-zA-Z0-9.-]*\.ngrok-free\.app"
```

把 `<該網址>/multi/player.html` 分享給區網外玩家（或轉成 QR code）。

**5. 主持人端**：維持原本習慣的方式開 `host.html`（Live Server 5500 或 `host-app`），不需要改變。

**結束時**：`Ctrl+C` 關閉 ngrok 與 Caddy 的終端機視窗即可；Mosquitto 是服務，預設會繼續留著背景執行，不影響其他用途，若真的要停用：

```bat
net stop mosquitto
```

> **注意**：免費版 ngrok 每次重啟通道網址會變（除非帳號有申請固定的 static domain），每次開放前需重新分享新網址給玩家。

## 常見問題與排除

### 玩家無法加入（一直顯示「MQTT 離線」）

1. 確認 Mosquitto 正在執行，且已啟用 WebSocket listener 9001
2. 確認 `MP_CFG.brokerIP` 與 `MP_CFG.wsPort` 正確
3. 防火牆是否開放 TCP 9001 埠
4. 主持人與玩家是否在同一網路下

### 玩家加入後畫面停在「等待主持人開始遊戲」

- 正常現象，等主持人點擊「開始遊戲」後即會自動同步
- 若主持人已開始但玩家沒動靜，檢查 MQTT 連線狀態徽章（右上角）

### 修改 `MP_CFG` 後無效

- 所有裝置均需**重新整理頁面**，`MP_CFG` 是前端常數，不會透過 MQTT 同步

### Live2D 角色不顯示

- 確認 `../lib/live2dcubismcore.min.js`、`../lib/pixi.min.js`、`../lib/all.min.js`、`../lib/live2d.js` 均可存取
- 玩家端可設 `enableLive2D: false` 跳過載入

### 拖曳角色時遊戲 UI 無法點擊

- 屬於設計行為：拖曳模式下 canvas z-index 提升至 9999 以接收滑鼠事件
- 再次點擊左下角對應的 `⠿` 按鈕取消拖曳即可恢復正常

### 想修改得分規則

調整 `MP_CFG` 中的四個參數：`MAX_SCORE`、`MIN_SCORE`、`MAX_PENALTY`、`MIN_PENALTY`，得分公式詳見[計分公式](#計分公式)章節。

## 學習報告模組重構與 bug 修正（2026-09-15 code review）

一次針對「今日修正」的程式碼審查揪出 10 個問題（bug、功能性問題、重複變數、冗餘代碼），全部修正並個別驗證。記錄在這裡方便之後追查為什麼會有這些寫法。

### 1. `bankFile` 對「自建題庫」等模式回報錯誤/過期資料

`sendStatsReports()` 原本用 `MP_CFG.QUESTION_BANK` 反推 `bankFile`，但 `MP_CFG.QUESTION_BANK` 只有 `loadBank(path)`（選真的 `questions/*.json` 檔案）才會設定；切到「自建題庫」（`__editor__`）、AI 生成題庫（`__ai__`）、尚未存檔的自訂上傳（`__custom__`）都不會更新它，導致學習報告的 `bankFile` 沿用**切換前**選到的舊題庫檔名。

修法：新增 `HS.currentBankFile` 這個明確的狀態欄位，在**每一個**會改變 `HS.allQ` 來源的地方都同步更新（`loadBank()`、`loadAIBank()`、`_applySavedBank()`、`bank-select` 的 `change` 監聽、`loadBankIndex()` 的初始化分支），`__editor__`/`__custom__`/`__ai__` 一律清成空字串。`sendStatsReports()` 改讀 `HS.currentBankFile`。

### 2. MQTT 重送造成學習報告統計被算兩次（全員作答制）

MQTT qos:1 是「至少送達一次」，同一則 `ANSWER` 訊息可能被重送。`onAnswer()` 原本的去重檢查（`HS.answeredIds.has(id)`）只放在「全員作答制」分支裡、且在**學習報告統計寫入之後**——分數確實不會被重複加（去重擋在加分之前），但 `HS.reactionTimes`/`HS.correctCounts`/`HS.domainStats`/`HS.wrongLog` 已經先寫過一次了，重送就會讓同一題被算兩次。

修法：把去重檢查搬到函式最上方、任何統計寫入之前。搶答制（`gameMode !== 'all'`）本來就靠 `phase`/`wrongIds` 的狀態轉換天然去重（同一 tick 內不可能有第二次 `onAnswer`），`answeredIds` 對搶答制永遠是空集合，搬到最上面對它沒有副作用。

### 3. `wrongQuestions` 上傳可能整場資料被 413 拒絕

`launchers/serve-lan.js` 的 `POST /api/record-session` 對整個請求 body 有 16KB 上限（`readJsonBody(req, 16*1024)`），超過會整包（連 `totalCorrect`/`domains` 一起）被拒絕，不是只丟掉超出的錯題。host.html 原本把 `HS.wrongLog[id]` 整包送出、不設上限，長題目/長解說的場次很容易踩到這個上限，且失敗時只有 `.catch(console.warn)`，主持人完全看不到。

修法：`_capWrongQuestionsForUpload()` 先比照伺服器端同樣的欄位長度上限做截斷，再依估算位元組數、從最近的錯題（最有參考價值）往前保留到 12KB 預算為止；真的被截掉或上傳失敗時額外用 `showToast()` 顯示警告，不只是印在 console。

### 4. 單題場次讓趨勢折線的顏色判斷失真

每局最低題數從 3 改成 1 之後，單題場次某個 domain 的準確率只會是 0% 或 100%，`_renderTrendSpark()` 原本直接拿「最後一場 vs 第一場」的準確率差判斷要畫綠色（進步）還是紅色（退步），單題場次的極端值很容易造成誤導。

修法：`_domainTrendPoints()` 改成回傳 `{v, n}`（準確率 + 該場作答題數），`_renderTrendSpark()` 只用樣本數 `n >= 2` 的頭尾兩筆資料判斷趨勢色，不足兩筆合格資料時維持 domain 識別色、不做進步/退步宣稱；折線本身仍畫出全部資料點，不因此失真。

### 5. `HS.correctCounts` 誤用暱稱當 key、`statsSlug`/`bankSlug` 檔名衝突、`readJsonBody` 逾量請求掛住連線

三個較小的修正：`HS.correctCounts` 統一改用 `id` 而非 `name` 當 key（跟其他 per-player 資料一致，避免同名玩家互相污染分數統計）；`launchers/serve-lan.js` 的 `statsSlug()`/`bankSlug()` 移除多餘的頭尾底線裁切，避免「Tom」跟「Tom!」轉成同一個檔名；`readJsonBody()`（`serve-lan.js` 與 `desktop-pet/control-server.js` 各一份）處理超量請求時改成不呼叫 `req.destroy()`（HTTP/1.x 底下會連 `res` 一起關掉，呼叫端收到的不是預期的錯誤訊息而是連線被重置），改用 `settled` 旗標防止重複 resolve/reject，讓超量請求能正常收到 413 回應。

### 6. 學習報告模組（~500 行 JS + ~90 行 CSS）重構為共用程式碼

「學習報告彈窗」整套邏輯（`openStatsModal`/`queryStatsReport`/`renderStatsReport`/`_renderDomainSection`/`_renderWrongQuestionsSection`/`_renderSessionHistorySection`/`_domainColor` 等）跟對應 CSS 原本在 `host.html`、`player.html` 各自維護一份幾乎一樣的複製貼上，改一邊很容易忘記改另一邊。

**JS**：搬到 `multi/multiplay.js` 共用。兩邊僅有的差異都用「呼叫端是否定義了某個全域函式」處理，不另外設計參數：
- `_statsDefaultName()`：開窗要預填的暱稱。`host.html` 定義成回傳 `HS.myName`，`player.html` 定義成回傳 `PS.myName`（退回 `localStorage` 記住的上次暱稱）。
- `recommendBank(bankFile, bankName)`：只有 `player.html` 定義，`_renderDomainSection()` 用 `typeof recommendBank === 'function'` 判斷，讓「推薦主持人多出這個範圍」按鈕在 `host.html` 自然不渲染。

`el('stats-name-select')?.addEventListener(...)` 這類**立即執行**的頂層事件綁定沒有搬過去——`multiplay.js` 是用 `<script src>` 在 `el`/`show`/`hide` 這幾個 DOM 小工具**被定義之前**載入的，函式定義本體沒問題（要等使用者點擊才會真的呼叫），但立即執行的敘述會撞到這個時序，所以繼續留在各自檔案裡。

**CSS**：搬到新檔案 `multi/stats-report.css`，兩邊都用 `<link rel="stylesheet">` 引入。唯一沒搬的是 `.stats-open-btn`（開啟按鈕本身）——這顆按鈕兩邊放置的情境/尺寸是真的不同（`player.html` 同時出現在加入畫面跟結算畫面，字級/留白比 `host.html` 大），各自留在自己的 `<style>` 裡。
